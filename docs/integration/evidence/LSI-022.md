## 1. Executive Summary & Objective

In accordance with [LSI-022](file:///Users/balveer/Projects/GraphMind/docs/integration/LEARNING_STUDIO_BACKLOG.md#lsi-022-owned-job-creation-status-and-result), the Learning Studio generator now consumes the LSI-021 goal-form handoff and drives the **existing owned job API** end to end:

1. **Idempotent, owned creation.** `StudioRoadmapGenerator` maps the LSI-021 `RoadmapRequest` onto `POST /roadmap/jobs` with a **stable `Idempotency-Key`** per request. A duplicate submit or a retry after an uncertain failure reuses the same key, so the server resolves to exactly one job (and `IDEMPOTENCY_MISMATCH` still rejects a changed body under the same key). Once a job is accepted, its id is retained for every later submission.
2. **Real event/status phases, no timers.** Progress is a pure projection of the owned job API: `useRoadmapJob` streams `GET /roadmap/jobs/{id}/events` (SSE) with `GET /roadmap/jobs/{id}` reconciliation and polling fallback, and `StudioJobProgress` renders the authoritative `status`, `stage`, `summary`, and persisted `JobEventData` feed. There is no local timer and no simulated completion.
3. **Completed-workspace navigation.** On a completed *published generation*, `completedRoadmapTarget` resolves the actual `workspaceId` / `roadmapId` / `revisionId` from the job result and the flow navigates through `buildWorkspaceUrl` (canonical `/w/{workspaceId}`), where the revision, protected `canvasAnchorChatId`, and saved profile resolve from the server curriculum API. Refinements/promotions resolve to proposals and are never auto-opened.

No production backend code changed: the ticket reuses `apps/api/src/routers/roadmap_jobs.py`, `services/roadmap/worker.py`, and `services/roadmap/job_repository.py` exactly as shipped. A focused backend test proves deterministic integrated generation against the isolated `_test` database.

## 2. Changes Made

### 2.1 Pure generation helpers (`apps/web/src/lib/studioGeneration.ts`, new)
* `requestFingerprint(request)` — order-independent fingerprint of the mapped `RoadmapRequest` (all LSI-020 extension fields included) used to decide key reuse.
* `JobKeyState` + `EMPTY_JOB_KEY_STATE` — the single client identity of an accepted submission (`fingerprint`, `key`, `acceptedJobId`).
* `nextJobKeyState(state, request, generateKey)` — same request keeps its key; a deliberately changed request before acceptance mints a new key; an accepted job id/key is retained. This is the "duplicate submit creates one job" rule on the client.
* `completedRoadmapTarget(job)` — returns `{ workspaceId, roadmapId, revisionId }` only for a completed published **generation**; `null` for running/failed jobs, refinements, and proposal results.

### 2.2 Server-driven progress panel (`apps/web/src/components/studio/StudioJobProgress.tsx`, new)
* Renders the authoritative snapshot heading per status (`completed` / `failed` / `canceled` / `awaiting_input` / active stage), the error or server `summary`, a `stage` badge, and the persisted event feed via the shared `JobActivity`.
* Shows the immutable submitted profile ("Your saved request") retained while the job runs.
* Offline/error notice ("Your generation stays saved on the server"), plus real Cancel / Retry / Create-another controls calling the owned endpoints. No client timers; completion never originates here.
* Strict `@/components/ui/` primitives (`Badge`, `Button`), semantic tokens, standard type scale; no raw `<button>` or arbitrary `text-[..]`.

### 2.3 Owned generation flow (`apps/web/src/components/studio/StudioRoadmapGenerator.tsx`, new)
* Consumes the LSI-021 `StudioGoalForm` `onSubmit(request, profile)` handoff.
* On submit: `nextJobKeyState` → `createRoadmapJob(request, key)` (idempotent) → `startRoadmapJob(jobId)` (idempotent enqueue) → watch with `useRoadmapJob`.
* A `submitting` ref plus the form's own disabled state prevent concurrent duplicate creates; the retained key/id collapse any that do occur to one server job.
* Completion effect reuses the proven `shouldOpenCompletedRoadmap` guard (same job, progress open, unchanged route) so a stale completed job never yanks the learner elsewhere. Navigation goes through `buildWorkspaceUrl` (never a hardcoded URL). A `failed`/`canceled`/`completed` job offers "Create another roadmap", which resets the idempotency state.

### 2.4 Surgical preview mount (`apps/web/src/app/studio-preview/page.tsx`)
* Replaced the LSI-021 stub `StudioGoalForm onSubmit={() => undefined}` with `<StudioRoadmapGenerator />` and swapped the single import. No other changes to this concurrently-edited file.
