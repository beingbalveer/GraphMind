## 1. Objective

Render the **actual** clarification question returned by the owned job API and wire the
existing `/roadmap/jobs/{id}/answers` route into the Learning Studio generator flow, so a
paused `awaiting_input` job can be answered from the real server contract without a scripted
or local clarification. The submitted profile and persisted event history are preserved
across the round trip, and refresh resumes the same job.

The backend contract already existed (`POST /roadmap/jobs/{job_id}/answers`,
`JobRepository.answer`, `ClarificationQuestion`, `PublicJobSnapshot.question`,
`useRoadmapJob().answer`). The gap was the frontend wiring: `StudioJobProgress` showed the
`awaiting_input` heading but no question/answer form, and `StudioRoadmapGenerator` never
passed the `answer` action through.

---

## 2. Changes Made

### 2.1 `apps/web/src/components/studio/StudioJobProgress.tsx`
* Added an `onAnswer: (questionId, answer) => Promise<unknown>` prop.
* Renders the existing shared `ClarificationForm` in a card (`data-testid="studio-job-question"`)
  whenever `job.question` is present, keyed by `job.question.id` so a **new** server question
  resets the form (and a resolved question removes it, since `question` becomes `null`).
* No local question, suggestions, or scripted answer: everything comes from the server snapshot.

### 2.2 `apps/web/src/components/studio/StudioRoadmapGenerator.tsx`
* Destructures `answer` from `useRoadmapJob` (already implemented in LSI-022) and passes it to
  `StudioJobProgress`, so answering calls the owned `/answers` route through the hook's
  `action` wrapper (which applies the returned snapshot and reconnects the stream).

### 2.3 Tests
* `apps/web/src/components/studio/__tests__/StudioRoadmapGenerator.test.tsx` (+3 tests):
  renders the owned question and submits exactly one suggested answer; shows no question form
  while the job is running; surfaces a stale `QUESTION_MISMATCH` rejection and keeps the
  pending question visible. The `useRoadmapJob` mock now exposes `answer`.
* `apps/api/tests/roadmap/test_jobs.py` (+1 test):
  `test_only_the_owner_can_answer_a_pending_question` — a non-owner answering raises
  `JOB_NOT_FOUND` and the job remains `awaiting_input` with its question intact.

## 4. Acceptance-Criteria Mapping

| Acceptance criterion | Evidence |
| :--- | :--- |
| Render actual clarification/questions and answer route | `StudioJobProgress` renders the server `job.question` via `ClarificationForm`; `StudioRoadmapGenerator` passes `useRoadmapJob().answer` → `POST /roadmap/jobs/{id}/answers`. Test: "renders the owned clarification question and submits one answer". |
| Preserve profile/history | The submitted profile card and `JobActivity` event feed remain rendered around the question; `useRoadmapJob` keeps the same `jobId` and stream across the answer, and `JobRepository.answer` appends to `clarification_context` (covered by `test_jobs.py`). |
| Only owned pending questions are answered | Backend: `test_only_the_owner_can_answer_a_pending_question` (`JOB_NOT_FOUND` for a non-owner; job stays `awaiting_input`). Route is owner-scoped via `get_roadmap_user`. |
| Duplicate/stale answers are safe | Backend: `JobRepository.answer` rejects a mismatched/stale `questionId` with `QUESTION_MISMATCH` (existing `test_waiting_answer_preserves_job_and_excludes_waiting_time`); frontend: "surfaces a stale answer rejection and keeps the pending question". `ClarificationForm` disables its controls while an answer is in flight. |
| Refresh resumes correct job | The form is a pure projection of the authoritative snapshot; on reload the same job id is re-read and `awaiting_input` is **not** terminal, so the stream/poll resumes and the question repaints. Test: "shows no clarification form while the job is still running" plus the LSI-022 `useRoadmapJob` reconnect coverage. |
| Out of scope honored (no scripted local clarification) | No client-authored question or answer text; the legacy demo `generation-clarification` scenario remains unmodified and unused. |
