## 1. Objective

Preserve the exposed AI refinement capability through its real services: a learner
requests a refinement (or resumes an interrupted one), the owned job produces a
**candidate proposal**, and the learner explicitly **applies** or **keeps** the
current plan. The active revision never changes until an explicit acceptance, a
stale/duplicate apply cannot silently overwrite newer work, and a failed or
interrupted refinement leaves the request editable so the learner can retry.

This is a parity/verification ticket: the refine/resume job, the proposal
diff/review, and the accept/reject routes already exist in the real services and
UI; LSI-037 proves the acceptance holds and closes the remaining evidence gap.

---

## 2. Design Decisions

* **No silent publish.** Publication of a refinement/promotion emits a
  `candidate` revision and its job result (`kind: "proposal"`,
  `proposal_state: "candidate"`); the roadmap's `current_revision_id` is untouched.
  `completedRoadmapTarget` deliberately never auto-opens a proposal, so the studio
  cannot navigate into an unaccepted change.
* **Explicit apply/reject.** `RevisionProposal` renders the diff and offers exactly
  two actions — **Apply changes** (`POST …/revisions/{id}/apply`) and **Keep
  current** (`POST …/revisions/{id}/reject`). Nothing is written before a click.
* **Stale/duplicate safety.** Apply carries the proposal's `baseRevisionId`;
  the server rejects a mismatch with `REVISION_CONFLICT`, the UI keeps the
  proposal and offers "Reload and regenerate". Replaying an applied proposal is a
  no-op and never overwrites a later edit.
* **Interrupted refinement recovers.** `RefinementModal` lists owned jobs, finds
  the latest non-applied/rejected refine job for the workspace, and resumes it
  (the LSI-024 owned-job recovery machinery) instead of starting a second run.
* **Errors leave the request editable.** A failed refinement start surfaces an
  alert but keeps the instruction/textarea and retry available, and reuses the one
  idempotency key for an unchanged instruction.
* **No new engine.** Reuses the existing refine job pipeline, revision service,
  and proposal model; no separate generation engine or proposal model is added.

## 3. Changes Made

LSI-037 verifies an existing capability. The only code change is a focused
regression test for the two acceptance points that were not explicitly asserted.

### 3.1 Frontend — `apps/web/src/components/roadmap/__tests__/refinement-modal.test.tsx`
* Extended the `@/lib/roadmapApi` mock with the proposal read/apply/reject
  functions so the completed-proposal branch can be exercised.
* New test: a failed refinement start keeps the instruction editable and a retry
  reuses the same idempotency key.
* New test: a completed refinement renders as a reviewable proposal, leaves the
  active revision untouched until **Apply changes**, and refreshes the view
  (`onSaved`) then closes.

### 3.2 Existing implementation verified (no code change)
* Backend: `RevisionService.request_refinement/proposal/apply/reject_proposal`,
  `PublicationService.publish` (candidate proposals), `curriculum` routes
  `/refinements`, `/revisions/{id}/proposal|apply|reject`.
* Frontend: `roadmapApi` (`requestRoadmapRefinement`, `readRoadmapProposal`,
  `applyRoadmapRevision`, `rejectRoadmapProposal`), `RefinementModal`,
  `RevisionProposal`, `RoadmapActions`, `RoadmapWorkspace`, `ResumeRefinement`,
  `studioGeneration.completedRoadmapTarget`, `useRoadmapJob`.

| Acceptance criterion | Evidence |
| :--- | :--- |
| Interrupted refinement recovers | `test_refinement_endpoint_seeds_base_and_replays_request` (backend) and the modal test "recovers a saved background refinement instead of starting another one" (frontend): the latest owned refine job resumes instead of a second run. |
| No silent publish/overwrite | Backend `test_refinement_publishes_proposal_without_replacing_current` (current revision unchanged), `test_proposal_waits_for_explicit_apply_and_preserves_completion`, `test_current_edit_survives_an_outdated_proposal`, `test_replaying_applied_proposal_never_overwrites_later_edit`, `test_stale_base_does_not_overwrite`. Frontend `refinement.test.tsx` "applies only after an explicit click" and the new modal "refreshes only on apply". |
| Errors leave the profile editable | New modal test: a failed start shows an alert but keeps the instruction value, the Generate action stays enabled, and a retry reuses the same idempotency key. `RefinementModal` keeps the base view and instruction on error; `RevisionProposal` keeps the proposal and offers regeneration on `REVISION_CONFLICT`. |
| Accept/reject/refresh journey | `refinement.test.tsx`: apply (with completion preserved), keep-current rejects only the candidate and preserves the active view, conflicting proposal offers reload/regenerate. New modal test: completed proposal → apply → `onSaved` + close. |
| No new engine / no new proposal model | Reuses the existing refine job pipeline and revision/proposal contracts; `test_branch_promotion.py` explicitly asserts no new proposal model. |
