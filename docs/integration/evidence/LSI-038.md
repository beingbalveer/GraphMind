## 1. Executive Summary & Objective

In accordance with [LSI-038](../LEARNING_STUDIO_BACKLOG.md#lsi-038-branch-promotion), branch promotion reuses the **existing** promotion → proposal → apply contract: a saved conversation branch is submitted through the existing `POST /promotions` endpoint, a `candidate` proposal revision is generated, reviewed via the existing `RevisionProposal` UI, and only applied on explicit confirmation. No new proposal model was introduced.

The work verified and hardened the ticket's acceptance criteria and added the previously missing focused evidence:

1. **Promoted topic links to the correct persistent node/root via `buildNodeUrl`:**
   - The lineage record (`CurriculumTopicOrigin`) persists the exact `source_workspace_id` / `source_chat_id` (persistent conversation root) / `source_node_id` (branch leaf) it was promoted from.
   - Both existing source-backlink surfaces format that triple through `@/lib/urls` `buildNodeUrl`: `TopicBriefDrawer` ("Added from exploration", `router.push`) and `RevisionProposal` ("Source conversation", `window.open`). No component hardcodes a URL.
2. **Source branch remains unchanged:**
   - Promotion publishes a new curriculum revision only. It never creates, rewrites, reparents, or deletes conversation nodes; asserted by comparing full node signatures before/after promotion and apply.
3. **Duplicates/conflicts are safe:**
   - Stale `baseRevisionId` → `409 REVISION_CONFLICT`; cross-workspace source node → `404`; missing `Idempotency-Key` → `422`; reuse of an idempotency key with different inputs → `IDEMPOTENCY_MISMATCH`; a repeated apply of an already-applied proposal returns the same revision with a single promoted topic and a single origin row.
   - Non-additive proposals are rejected by the existing `PROMOTION_NOT_ADDITIVE` guard (pre-existing coverage in `test_publication.py`).

No production source was modified. This ticket adds focused tests that pin the acceptance behavior and documents it.

## 2. Changes Made

### 2.1 Backend promotion API/lineage tests (`apps/api/tests/roadmap/test_branch_promotion.py`, new)
Three focused pytest tests plus helpers, reusing the shipped promotion/lineage/publish contracts:

- `test_promoted_topic_links_back_to_exact_persistent_source_branch` — drives `PublicationService.publish` for a promotion and asserts the persisted origin equals the exact `(workspace, root, leaf)` triple, that the composed link equals the canonical `buildNodeUrl` shape `/w/{ws}/chat/{chat}?node={node}`, that both nodes exist in the workspace, and that the change is additive (all original active topics remain).
- `test_promoting_leaves_source_branch_unchanged_and_reapply_is_safe` — snapshots every node signature before promotion and asserts nothing changed after apply; re-applies the same proposal and asserts the same revision id, exactly one promoted topic, and exactly one origin row.
- `test_promotion_api_requires_idempotency_and_rejects_conflicts` — exercises the HTTP endpoint `POST /api/v1/workspaces/{workspace_id}/roadmap/promotions`: missing `Idempotency-Key` → `422`, stale base → `409 REVISION_CONFLICT`, cross-workspace source → `404`; the active roadmap revision is unchanged after rejections.

### 2.2 Frontend source-backlink tests (`apps/web/src/components/roadmap/__tests__/branch-promotion-backlink.test.tsx`, new)
Three focused vitest tests for the promoted topic's source backlink on the lesson brief:

- Renders "Added from exploration" provenance and navigates with `buildNodeUrl("ws", "source-root", "branch-leaf")` (no hardcoded path).
- Renders the honest "The source conversation is no longer available." state with no link when the origin is `unavailable`.
- Renders no provenance for a topic that was not promoted (origin scoped by `topicId`).

Existing promotion tests were re-run unchanged (no edits to shared test files).
