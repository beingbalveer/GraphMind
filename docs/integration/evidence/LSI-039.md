## 1. Objective

Port the existing provider / key / model / system-skill selectors and their
supported request behavior into the integrated Learning Studio, and document the
browser-local key model. A valid selection must reach the **real tutor** and the
**real generator request**; a missing or invalid provider must be actionable; and
provider secrets must never enter docs, logs, exports, or any public DTO.

This is largely a parity/verification ticket — the production selectors, the
server-side BYOK resolution, and the chat skill surface already exist — with one
real parity gap fixed: the Learning Studio tutor dropped the learner's provider
credentials.

---

## 2. Existing capability verified (no code change)

* **Provider / key / model selectors** — `apps/web/src/components/settings/SettingsModal.tsx`
  and `SettingsPage.tsx` expose the full provider matrix (Gemini, Claude, OpenAI,
  DeepSeek, Ollama, Mock), per-provider BYOK key inputs, the active model, the
  system instructions, and the Ollama base URL. `useModelConfig` persists them to
  `localStorage` (`graphmind:llm-config`) only.
* **Supported request behavior** — `ChatContainer` forwards
  `provider`/`model`/`apiKey`/`baseUrl`/`temperature`/`maxTokens`/`systemPrompt`/`enabledSkills`
  into the real `/chat/stream` request; `useChatStream` maps them onto the wire
  fields `provider`, `model`, `api_key`, `base_url`, `temperature`, `max_tokens`,
  `system_prompt`, `enabled_skills`.
* **System-skill selector** — `ChatInput` slash commands (`/research`, `/code`,
  `/quiz`) select the `deep_research` / `code_architect` / `quiz_master` system
  skills, which are sent as `enabled_skills` and injected server-side via
  `SkillRegistry.build_system_prompt`.
* **Server-side BYOK + actionable errors** — `routers.chat._resolve_api_key`
  prefers the client key over the environment; a lesson request whose provider
  resolves to the mock fallback raises `503 MODEL_NOT_CONFIGURED`
  ("Configure a real chat provider to start this lesson.", `recoverable`,
  `next_action: retry`); the generator raises the same code via
  `configured_provider`.
* **Secrets stay out of logs/exports/public DTOs** — `chat.py` logs only
  `has_api_key=bool(api_key)`; exports serialize the conversation graph
  (`provider`/`model` only); no public DTO carries a credential.

## 3. Changes Made

### 3.1 Runtime fix — `apps/web/src/components/studio/StudioTutorChat.tsx`

The Learning Studio tutor (the ported learner surface) previously forwarded only
`provider` + `model` to `sendMessage`, dropping the learner's effective BYOK key,
custom base URL, temperature, and max tokens. With only a browser-local key
configured on a non-default provider, the lesson tutor fell back to the server's
Mock provider and failed `MODEL_NOT_CONFIGURED` even though a valid key was set.

* `useModelConfig()` now yields `getEffectiveApiKey` / `getEffectiveBaseUrl`, and
  the tutor request forwards `apiKey`, `baseUrl`, `temperature`, and `maxTokens`
  exactly as the main conversation does.

### 3.2 Documentation — `apps/web/src/hooks/useModelConfig.ts`

Added the canonical **browser-local key model** JSDoc: provider/model/params and
BYOK keys live only in this browser's `localStorage`, a key is attached per
request as the optional `api_key`, blank keys resolve to `undefined` so the
server environment fallback applies, and secrets never appear in exports or
public DTOs.

### 3.3 Tests

* `apps/web/src/components/settings/__tests__/provider-settings.test.tsx` (new, 4) —
  full provider matrix rendered + selection mapped onto the saved config;
  `useModelConfig` keeps the key browser-local, resolves it per provider, and
  makes no network call; a blank key drops to the server fallback; exports carry
  the graph but never a secret.
* `apps/web/src/hooks/__tests__/useChatStream.provider.test.tsx` (new, 2) —
  provider/BYOK/generation-params/system-skill forwarded into the request; an
  unconfigured selection omits `api_key`/`enabled_skills`.
* `apps/web/src/components/studio/__tests__/StudioTutorProvider.test.tsx` (new, 1) —
  the tutor forwards the effective provider/key/temperature/max tokens.
* `apps/web/src/components/chat/__tests__/chat-input.test.tsx` (+1) — a slash
  command selects a system skill and forwards it with the message.
* `apps/api/tests/test_provider_settings.py` (new, 5) — BYOK precedence + env
  fallback + unknown-provider `None`; chat skill surface excludes roadmap
  playbooks; unknown skill ignored / known skill injected; missing provider is an
  actionable recoverable `MODEL_NOT_CONFIGURED`; a BYOK secret is never logged.

## 6. Limitations

* Live provider quality is out of scope here (mocked/local evidence only); the
  live provider/research-quality gate is LSI-048.
* The generator (`/roadmap/jobs`) intentionally resolves its provider from server
  configuration; client provider selection affects the tutor and the main
  conversation, not the owned generation pipeline.
* The Learning Studio tutor displays a topic-specific system prompt; the
  "System Instructions" setting affects the main conversation and the request
  parameters (temperature/tokens/key) for the tutor, not its topic persona.
