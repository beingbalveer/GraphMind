## 1. Executive Summary & Objective

In accordance with [LSI-042](file:///Users/balveer/Projects/GraphMind/docs/integration/LEARNING_STUDIO_BACKLOG.md#lsi-042-knowledge-signals-and-curator-parity), the workspace's **explicit** learning signals — tracked concepts, mastery levels, detected knowledge gaps, gap adoption, and next-topic recommendations — are surfaced and locked through the **existing** mastery/curator services. No new curator feature, endpoint, or mastery rule was invented, and no model/schema/migration was changed.

The work delivers:

1. **A reachable learning-signals surface (`KnowledgeSignalsPanel`)** that reads the existing `GET /workspaces/{id}/mastery`, `GET /workspaces/{id}/curator/gaps`, and `GET /workspaces/{id}/curator/next-topics` endpoints and calls the existing `POST /workspaces/{id}/curator/gaps/{gapId}/adopt` action. It is opened from the canvas actions menu on the conversation canvas, alongside the existing "Show mastery" and "Open timeline" controls.
2. **The distinctness invariant stated and enforced.** The panel says plainly that concept mastery comes from quizzes/explicit reviews and *stays separate from lesson completion*; the backend locks that completing a topic creates **zero** mastery signals and that `mastered` is not a valid completion status.
3. **Persistence and authorization locks.** Focused pytest tests assert that concept/quiz/gap/adopt state persists across requests, that viewers may read every signal but not mutate them (`403`), and that non-members see indistinguishable `404`s for both reads and writes.

Existing production tray consumers were preserved: `QuizCard` (`createWorkspaceConcept` → `updateWorkspaceConcept`) remains the explicit quiz→mastery feedback path, and `GraphCanvas` heatmap/timeline consumers are unchanged. The `concept-mastery-updated` DOM event remains the canonical reactive refresh signal, now also dispatched by gap adoption.

## 2. Changes Made

### 2.1 Frontend — Learning signals panel (`apps/web/src/components/canvas/KnowledgeSignalsPanel.tsx`, new)
* Loads the existing workspace mastery summary, knowledge gaps, and next-topic recommendations via `@/lib/workspaceApi` (no new client or endpoint).
* Renders: overall mastery score + distribution badges (`mastered`/`quizzed`/`explored`/`stale`/`unexplored`), the tracked-concept list with per-concept confidence and level, prioritized knowledge gaps with an **Adopt gap** action, and curator next-topic recommendations with readiness.
* States the explicit-signal invariant in an `InlineFeedback` banner; uses honest loading, empty, and "unavailable" states (`EmptyState` / `InlineFeedback`).
* Adopt calls the existing `adoptKnowledgeGap`, then dispatches the canonical `concept-mastery-updated` event so the panel and any open canvas heatmap refresh from persisted state. A denied write is reported honestly ("needs write access to this workspace") and leaves the UI unmodified.
* Strictly uses shared primitives (`Badge`, `Button`, `InlineFeedback`, `EmptyState`, `Skeleton`) and semantic tokens; no raw `<button>` and no hardcoded `zinc-*` colors.

### 2.2 Frontend — Canvas mount (`apps/web/src/components/canvas/GraphCanvas.tsx`, +19 lines)
* Adds a `showSignals` state, a `"Knowledge signals"` item to the existing canvas actions menu (only when a `workspaceId` is present), and a shared `Drawer` hosting the panel. The existing menu entries and all other canvas behavior are untouched.

### 2.3 Backend — Focused acceptance suite (`apps/api/tests/roadmap/test_knowledge_signals_lsi042.py`, new)
Three tests against the existing services and the isolated `*_test` database:
* `test_explicit_mastery_signal_is_distinct_from_topic_completion` — completing a topic leaves `GET /mastery` at zero concepts; `status: "mastered"` on the progress route is rejected with `422`; an explicit mastery concept does not complete or alter any topic.
* `test_knowledge_signal_actions_persist` — create concept → detected gap → adopt → re-read lists the adopted concept and moves the gap `missing` → `unexplored`; quiz feedback persists on the concept; recommendations remain observable.
* `test_knowledge_signal_actions_are_authorized` — a viewer reads all signals (`200`) but is denied every write (`403`); a non-member receives `404` for both reads and writes; the owner's adopt still succeeds (`201`).

### 2.4 No runtime backend changes
* No router, service, schema, model, or migration was modified. The mastery/curator services already exposed every action the ticket preserves.

## 6. Limitations
- The panel is mounted on the conversation canvas (`GraphCanvas`) actions menu; the curriculum canvas (`RoadmapCanvas`, used by the studio course list) was left unchanged to keep shared-file edits minimal. The same workspace-level signals therefore render wherever the conversation canvas is reachable.
- `/studio-preview` and the legacy `MasteryPanel` remain out of scope: the removed panel (`46bd69c`) used hardcoded zinc colors and ad-hoc markup, so it was not revived; the new panel is a fresh, design-compliant surface over the same services.
- Verification used focused suites plus `tsc --noEmit` and `ruff`; `next build` and the full suites were skipped per the ticket instructions.
- During this session, concurrent agents share the `graphmind_test` database; a focused regression run that crosses their cleanup boundary (`DELETE FROM workspaces;`) can transiently fail for unrelated tests. Every focused suite above was re-run and passed in isolation.
