## 1. Objective

Approve a **versioned export** of caller-owned data that can never leak
credentials or internal storage, and settle the **reset/delete boundaries** so a
learner can tell a local settings reset apart from an irreversible account or
workspace deletion. Destructive actions must confirm, and failures must keep the
UI and data consistent.

Before this ticket there was no server-side export at all — the only "export"
was the client-side `WorkspaceModal` graph dump, which is not mounted in
production — and the Settings footer reset was labelled ambiguously
("Reset settings to defaults").

---

## 2. Changes Made

### 2.1 Backend — versioned, allowlisted export

* `apps/api/src/schemas/export.py` — `EXPORT_VERSION = "1"` and allowlist
  response schemas (`WorkspaceExportResponse`, `ExportWorkspaceMeta`,
  `ExportNode`, `ExportEdge`, `ExportConcept`, `ExportFlashcard`, `ExportFile`,
  `ExportCounts`) built with `from_attributes=True` and camelCase aliases.
  Because each entity is modelled as an explicit field allowlist, node/concept
  `metadata` JSON, pgvector `embedding`, file `storage_path`, and any credential
  material can never serialize.
* `apps/api/src/services/workspace_export_service.py` —
  `WorkspaceExportService.build_export` reads the workspace's nodes, edges,
  concepts, flashcards, and files (deterministic ordering) and validates each row
  into its allowlisted export schema; returns a versioned archive with a
  `counts` summary.
* `apps/api/src/routers/workspaces.py` — new
  `GET /api/v1/workspaces/{workspace_id}/export` gated by
  `require_workspace_read`, returning `WorkspaceExportResponse`.

### 2.2 Frontend — export control and explicit boundaries

* `apps/web/src/lib/workspaceApi.ts` — `WorkspaceExportArchive` type and
  `exportWorkspace(workspaceId)` calling the new endpoint (surfacing failures).
* `apps/web/src/lib/exportUtils.ts` — `exportWorkspaceArchive(archive, title)`
  serializes the server-shaped archive to pretty JSON and downloads it under a
  title-derived `<workspace>_workspace_export.json` filename.
* `apps/web/src/components/settings/SettingsPage.tsx` — new **Data ownership**
  section in the Workspaces tab with an **Export data** button (loading-aware,
  inline error on failure, disabled with no workspace in scope). The reset dialog
  is relabelled **"Reset local settings"** and its description states it restores
  this browser's model settings and keys only — it does **not** delete the
  account, workspaces, or conversations. The section copy repeats that boundary
  and that export never includes provider keys or internal storage.
* `apps/web/src/components/chat/ChatContainer.tsx` — `handleExportWorkspace`
  fetches the archive and triggers the download; failures propagate so Settings
  reports them. Passed into `SettingsPage` as `onExportWorkspace`.

Destructive workspace deletion (with `ConfirmDialog`) already lives in
`WorkspaceDashboard` from LSI-040 and is unchanged; this ticket only clarifies
the boundary between it and the local reset.

## 4. Acceptance-Criteria Mapping

| Acceptance criterion | Evidence |
| :--- | :--- |
| Export includes only caller-owned permitted data | `test_workspace_export_returns_versioned_owned_data` — only the requested workspace's nodes/edges/concepts/etc. with matching `counts`. |
| No credentials / provider keys in the export | `test_workspace_export_excludes_credentials_and_internal_fields` asserts the raw response contains no key/secret/`system_prompt`/`storage_path`/`embedding`/`password` strings; node keys equal the allowlist exactly (no `metadata`). |
| Ownership enforced | `GET .../export` depends on `require_workspace_read`; `test_workspace_export_requires_membership` proves a non-member is denied. |
| Versioned export | `exportVersion == "1"` asserted in the owned-data test and by the frontend download wrapper. |
| Destructive actions confirm | Workspace deletion uses the shared `ConfirmDialog` (`WorkspaceDashboard`, LSI-040, covered by `workspace-management.test.tsx`); this ticket's reset uses `ConfirmDialog` too. |
| Local reset distinguished from account/workspace deletion | `export-settings.test.tsx` locks the "Reset local settings" title and the "does not delete your account, workspaces, or conversations" copy. |
| Failures keep UI/data consistent | Failed export shows an inline alert and re-enables the control for retry (no navigation, no data change); backend export is read-only. |

## 5. Limitations

* The downloaded archive's live round-trip against a populated production
  workspace is exercised by the integration gate (LSI-046); this ticket evidences
  the API contract, privacy allowlist, client wrapper, and boundaries.
* Account-level deletion is not a separate endpoint in the current product;
  account/workspace deletion remains the existing workspace-delete path, and the
  copy avoids implying a new destructive surface.
* Obsolete learner UI / `WorkspaceModal` retirement is LSI-050.
